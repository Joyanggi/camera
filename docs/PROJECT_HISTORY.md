# 프로젝트 히스토리와 의사결정

## 출발점

이 프로젝트는 “재입고 공지를 봐도 수량이 적어 구매 페이지를 열었을 때는 이미 품절”이라는 개인적인 문제에서 시작했습니다. 이전에 다른 품귀 상품을 30초 간격으로 확인해 구매에 성공한 경험을 카메라 재고 확인으로 확장했습니다.

처음에는 맥북 터미널에서 캐논과 네이버 판매처를 반복 확인하는 작은 Python 스크립트였습니다. 이후 구매 대상이 Sony RX100M7과 RICOH GR IV로 바뀌고 판매처가 늘면서, 단일 스크립트가 판매처별 어댑터·통합 실행기·Slack 알림·웹 대시보드를 갖춘 운영형 프로젝트로 발전했습니다.

## 고민과 해결

| 고민 | 관찰 | 해결 |
| --- | --- | --- |
| 무엇을 재고 신호로 믿을 것인가 | 화면의 `품절` 문구와 내부 재고 값이 항상 같지 않음 | JSON-LD, API 응답, 재고 수량, 판매 상태, 버튼 상태를 함께 판정 |
| polling을 얼마나 자주 할 것인가 | 빠를수록 구매 확률은 높지만 429와 IP 차단 위험도 증가 | 로컬은 최소 주기·랜덤 jitter, 403/429는 별도 백오프, 클라우드는 10분 주기 |
| 차단과 인터넷 장애를 어떻게 구분할 것인가 | 핫스팟에서 DNS 실패와 `No route to host`가 반복됨 | HTTP 제한 응답과 DNS·timeout·connection 오류를 별도 상태로 분류 |
| 터미널을 못 보고 있을 때 어떻게 알 것인가 | 로그만으로는 즉시 대응하기 어려움 | 시스템 알림음, Slack Webhook, 브라우저 Notification과 Web Audio 추가 |
| 여러 번 같은 알림이 오는 문제 | 재고가 유지되는 동안 매 주기 알림 가능 | 이전 상태를 저장하고 `SOLD_OUT → BUYABLE` 전환에서만 알림 |
| 일시 오류가 재고 변화처럼 보이는 문제 | 외부 사이트 한 곳의 실패가 대시보드 전체 신뢰도를 낮춤 | 마지막 정상 상태를 유지하고 `stale` 및 실패 원인을 별도 기록 |
| 맥북을 계속 켜야 하는 문제 | 로컬 프로세스와 네트워크에 운영이 종속됨 | GitHub Actions에서 통합 checker 실행, Vercel 정적 대시보드 배포 |
| Windows에서 한글이 깨지는 문제 | 콘솔 code page와 Python 입출력 인코딩 차이 | `chcp 65001`, `PYTHONUTF8`, `PYTHONIOENCODING` 설정 |

유쾌한생각 상품을 추가했습니다. EUC-KR/CP949 응답을 명시적으로 디코딩하고 `ENP_VAR.soldOut`, `sto_state` 같은 쇼핑몰 내부 신호를 사용했습니다.

### 2026-06-11 · 로컬 스크립트에서 운영 시스템으로

모든 모니터를 호출하는 `aggregator/check_all.py`, 공통 `status.json`, 10분 주기 GitHub Actions, Vercel 대시보드를 추가했습니다. Slack 테스트 모드, 브라우저 알림, 테스트용 가상 구매 가능 카드와 알림음을 더해 운영 전에 알림 경로를 검증할 수 있게 했습니다.

네트워크 오류가 재고 상태를 덮어쓰지 않도록 마지막 정상 상태 carry-forward를 도입했습니다. 이후 stale detail이 반복 실행 때 계속 길어지는 문제를 발견해 원본 `last_good_detail`과 시각을 고정하는 방식으로 수정했습니다.

### 2026-07-14 · 목표 달성 및 운영 종료

목표 상품 구매에 성공해 scheduled workflow를 제거했습니다. 마지막 상태와 대시보드는 재현 가능한 포트폴리오 스냅샷으로 보존했습니다.

## 기술적으로 중요했던 선택

1. **브라우저 자동화보다 HTTP 파싱을 우선했습니다.** 자원 사용량과 실행 시간을 낮추고 GitHub Actions에서도 안정적으로 실행하기 위해서입니다.
2. **공통 상태 모델을 만들었습니다.** 판매처 원본 값은 달라도 `BUYABLE`, `SOLD_OUT`, `UNKNOWN`, `NETWORK_ERROR`, `RATE_LIMITED`로 통일했습니다.
3. **알림은 event로 취급했습니다.** 현재 상태 자체가 아니라 이전 상태와의 차이를 계산해 한 번만 전송했습니다.
4. **실패 시 확신을 낮췄습니다.** 네트워크 실패를 품절로 간주하지 않고 마지막 정상 상태와 stale 표식을 함께 보여줬습니다.
5. **종료 조건을 운영에 포함했습니다.** 구매 성공 후 scheduled workflow를 중단해 불필요한 요청과 GitHub Actions 실행을 멈췄습니다.

## 회고

빠른 polling만으로는 신뢰할 수 있는 모니터가 되지 않았습니다. 외부 사이트의 인코딩과 HTML 구조, rate limit, DNS 장애, 오래된 상태를 모두 구분해야 사용자가 실제로 행동할 수 있는 알림이 됐습니다.

다시 만든다면 판매처 어댑터 인터페이스를 초기에 명확히 정의하고 fixture 기반 파서 테스트를 더 일찍 추가할 것입니다. 또한 상태 기록을 매번 Git 커밋하는 대신 작은 저장소나 캐시를 사용해 운영 데이터와 소스 이력을 분리할 것입니다.
