# 이력서·면접용 정리

이 문서는 README보다 짧고 채용 문맥에 맞는 표현을 모아둔 초안입니다. 지원 포지션에 맞춰 2~3개 bullet만 선택해 사용하는 것을 권장합니다.

## 한 줄 소개

여러 쇼핑몰의 비정형 재고 신호를 공통 상태로 정규화하고, GitHub Actions·Slack·Vercel로 무인 운영한 카메라 재고 모니터링 시스템입니다.

## 이력서 Bullet

- Python Requests와 BeautifulSoup으로 6개 국내 판매처·9개 상품의 JSON-LD, 재고 수량, 판매 상태, 버튼 신호를 분석하는 사이트별 어댑터를 구현했습니다.
- 판매처별 결과를 공통 상태 모델로 정규화하고 `SOLD_OUT → BUYABLE` 전환에서만 Slack을 보내 반복 알림을 제거했습니다.
- HTTP 403/429 백오프, 랜덤 polling 간격, DNS·timeout 재시도, 마지막 정상 상태 carry-forward를 적용해 외부 사이트 장애가 오탐으로 이어지지 않도록 했습니다.
- GitHub Actions 10분 주기 실행과 Vercel 대시보드로 로컬 PC 의존성을 제거하고, 약 2개월 실운영 끝에 목표 상품 구매에 성공했습니다.
- macOS 시스템 사운드와 Windows UTF-8 콘솔·알림을 지원해 동일한 모니터를 두 운영체제에서 실행 가능하게 구성했습니다.

## STAR 답변

### Situation

인기 카메라가 여러 공식몰과 전문몰에 극소량으로 불규칙하게 입고됐고, 공지를 확인한 뒤 접속하면 이미 품절되는 경우가 많았습니다.

### Task

컴퓨터 화면을 계속 지켜보지 않아도 여러 판매처를 자동 확인하고, 실제 구매 가능한 순간만 신뢰도 있게 알려주는 시스템이 필요했습니다.

### Action

판매처 HTML과 API 응답을 분석해 사이트별 재고 어댑터를 구현했습니다. 서로 다른 신호를 공통 상태로 변환하고 이전 상태와 비교해 구매 가능 전환을 감지했습니다. 운영 중 발생한 429, DNS 실패, timeout을 구분하고 백오프·재시도·stale 상태 보존을 추가했습니다. 이후 GitHub Actions와 Vercel로 이전해 Slack과 웹 알림이 동작하는 무인 흐름을 만들었습니다.

### Result

6개 판매처 9개 상품을 약 2개월 동안 운영했고, 목표 상품 구매에 성공했습니다. 목적 달성 후 scheduled workflow를 종료하고 코드, 최종 상태, 대시보드와 장애 대응 기록을 포트폴리오로 정리했습니다.

## 면접에서 설명할 포인트

- **왜 Selenium이 아닌 Requests인가?** 정적·구조화 신호가 충분한 사이트는 HTTP 요청이 더 빠르고 저렴하며 Actions 러너에 적합했습니다.
- **오탐을 어떻게 막았나?** 단일 문구보다 여러 재고 신호를 조합하고, 네트워크 실패는 상태 변화로 취급하지 않았습니다.
- **Slack 중복 알림은 어떻게 막았나?** URL별 이전 상태를 저장하고 BUYABLE 전환만 event로 만들었습니다.
- **운영 중 가장 어려운 문제는?** 서로 다른 사이트보다 429와 일시 네트워크 오류를 구분하고 마지막 정상 상태의 신뢰도를 유지하는 일이었습니다.
- **다시 개선한다면?** HTML fixture 기반 파서 테스트, 어댑터 프로토콜, Git과 분리된 상태 저장소를 도입하겠습니다.

## 기술 키워드

`Python` · `Requests` · `BeautifulSoup` · `Web Scraping` · `State Transition` · `Retry/Backoff` · `GitHub Actions` · `Slack Webhook` · `Vanilla JavaScript` · `Vercel`

## 과장하지 않기 위한 경계

- 클라우드 운영 주기는 10분이었으며 초 단위 실시간 시스템은 아닙니다.
- 공식 재고 API가 없는 판매처는 HTML 구조 변경에 영향을 받을 수 있습니다.
- 별도 데이터베이스 없이 `status.json`을 사용한 개인 프로젝트 규모의 설계입니다.
- 결과는 “매출 향상”이 아니라 실제 개인 구매 목표 달성입니다.
